# 生成 Git 提交信息

生成简洁、准确的提交信息，描述当前改动的主要意图，并遵循仓库自身的提交规范。

## 工作流程

1. 阅读当前范围内生效的 `AGENTS.md`，以及其他定义提交规范的仓库文档。
2. 在不修改仓库的前提下检查当前状态：
   - 运行 `git status --short`。
   - 运行 `git diff --cached --stat` 和 `git diff --cached`。
   - 如果暂存区没有差异，运行 `git diff --stat` 和 `git diff`，并明确说明建议基于未暂存改动。
   - 必要时检查相关的未跟踪文件，不得仅根据文件名猜测其内容。
   - 运行 `git log -10 --pretty=format:%s`，了解仓库近期提交所用的语言和风格。
3. 暂存区存在改动时，仅根据暂存改动生成提交信息。除非用户明确要求涵盖工作区全部改动，否则不得混入未暂存改动。
4. 判断改动的主要意图，并选择仓库允许的提交类型。如果仓库没有相关规范，则使用 Conventional Commits 中的常见类型，例如 `feat`、`fix`、`refactor`、`test`、`docs`、`build`、`chore` 或 `style`。
5. 检查是否存在互不相关的改动。如果差异包含多个独立事项，应建议拆分提交，并为每个逻辑提交分别生成信息，不得用含糊的主题掩盖多个事项。
6. 提交主题应具体、使用祈使表达，末尾不加句号。语言和风格应与仓库规范及近期提交保持一致。
7. 仅在需要解释改动动机、重要行为、迁移影响或不明显的约束时添加正文。正文不得只是重复主题。

## 输出格式

首先在便于复制的代码块中给出最佳建议，并说明建议基于暂存还是未暂存改动。只有当其他表述或类型选择确实有不同含义时，才提供备选，最多两个。

单个逻辑改动使用以下格式：

```text
依据：已暂存改动

fix: 修复目录移动后的上下文路径同步
```

需要正文时，在同一代码块的主题后空一行再添加正文。对于不确定之处、缺少的上下文或拆分提交建议，在代码块外简要说明。

## 安全边界

- 只能使用只读的 Git 命令和文件系统检查命令。
- 禁止运行 `git add`、`git commit`、`git commit --amend`、`git push`、标签相关命令，以及任何会丢弃改动的命令。
- 不得编造问题编号、作用域、破坏性变更标记、测试结果或无法从实际改动中确认的实现细节。
- 不得泄露密钥，也不得在回答中复述敏感文件的内容。
